# AutoJobApplyAgent

Java 21 IntelliJ application for high-volume, legitimate job applications. Its future objective is hundreds of relevant confirmed applications from one Run action; this is a product goal, not a claim of current results.

## Workflow

`Main.java → ATS company discovery → job retrieval → filtering → resume matching → persistent queue → ATS adapter → verified submission → SQLite/CSV`

The system must not require manual company lists, board tokens, or job URLs. A discovered job is never a submitted application.

## Targeting

Principal, Staff, Senior Staff, Lead, Architect, and equivalent backend/platform roles; Java, Spring Boot, Kafka, cloud, and distributed systems; Bay Area and eligible remote-US jobs; configurable 60% minimum score; mandatory eligibility overrides score.

## ATS roadmap

1. Greenhouse: public board discovery, validation, job retrieval, matching, queueing, authorized form submission, confirmation.
2. Oracle Fusion Cloud Recruiting.
3. Workday.
4. Lever.

Only Greenhouse is in scope now.

### Playwright status

Native IntelliJ `Greenhouse DRY RUN` has launched Playwright against one public live Greenhouse form: Broadsign’s `Salesforce Solution Architect` (`broadsign|7963904003`). Using only the ignored fictional Jordan Rivera profile and fictional resume, the adapter verified the actual DOM values for first name, last name, email, country, phone, location, LinkedIn profile, and the explicit answer `No` to “Are you located in Montreal, QC, Canada?” It also verified the visible resume attachment. The resulting validation record is `READY_FOR_SUBMISSION_IN_DRY_RUN`, with `submit_attempted=0`. Subsequent job-eligibility revalidation correctly marked that queue record `INELIGIBLE`: the role’s substantive Salesforce administration and certification requirements are not evidenced by the fictional Java backend profile. The browser-validation evidence remains retained and is independent of eligibility.

This is evidence for that form pattern only, not a claim of universal Greenhouse support or a submitted application. Other forms may contain different required questions and must remain `NEEDS_MANUAL_ACTION` unless a compatible, explicit applicant-profile answer and DOM validation are available.

## Greenhouse Step 2

Greenhouse has no global board API. The next implementation ingests a legitimate public directory, validates tokens through `boards-api.greenhouse.io/v1/boards/{token}/jobs?content=true`, persists valid employers, refreshes open jobs, filters/matches them, and queues eligible work. Coverage is measured, never treated as universal.

## Run locally

1. Open `pom.xml` with Java 21 in IntelliJ.
2. Keep the resume at `private/resume.docx` or configure `job.resume.path`.
3. Copy `private/applicant.properties.example` to ignored `private/applicant.properties`; use verified answers only.
4. Run `com.autojobapply.Main`.

`data/applications.db` is authoritative; `data/applications.csv` is its report. Keep `authorized.submission.enabled=false` until a platform adapter is validated. `SUBMITTED` requires genuine employer confirmation.

For real-form validation outside Codex, select the checked-in **Greenhouse DRY RUN** IntelliJ configuration. Its JVM properties force `DRY_RUN`, `job.auto.submit=false`, and `authorized.submission.enabled=false`; changing the resource file cannot cause that configuration to click Submit.

That configuration also forces `private/dry-run/resume.docx` and `private/dry-run/applicant.properties`. These ignored files contain only fictional data generated by `CreateSyntheticDryRunAssets`; they never copy, read, or fall back to the real resume or applicant profile. If either file is unavailable, DRY_RUN stops before loading any applicant data.

The profile supports explicit factual values such as `work.authorization.answer`, `sponsorship.required.answer`, `immigration.i140.approved.answer`, `experience.years`, `education.degree`, `relocation.answer`, `compensation.expectation`, `skills.verified`, and `employment.1.*`. These are distinct facts; missing or ambiguous answers remain unresolved. For recognized written prompts, the Greenhouse resolver can compose a bounded response only from explicit years, verified skills, summary, employment highlights, and matching job-description terms. It does not use a model provider or invent facts.

For a bounded inspection of an existing queue item, an IntelliJ debugging session can set the opt-in JVM property `job.queue.identity` before configuration loading. It loads only that `READY_TO_APPLY` record from SQLite and skips all employer discovery. This is intended for a single controlled DRY_RUN check; ordinary runs leave the property unset and follow the discovery pipeline.

## Execution safety modes

`job.execution.mode=DISCOVER_ONLY` is the default: it discovers, matches, and queues positions without opening forms. `DRY_RUN` may open and validate a supported form but never clicks Submit. `LIVE` requires both `job.auto.submit=true` and `authorized.submission.enabled=true`; it starts with `job.max.submissions.per.run=1` and stops additional LIVE work after the configured validation-failure threshold. Required unknown fields, missing resume attachments, visible errors, incomplete screening answers, and unverified confirmations result in `NEEDS_MANUAL_ACTION` or `NEEDS_VERIFICATION`, never `SUBMITTED`.

Local Step 3 fixture tests cover complete forms, missing required values or resume attachments, unanswered required screening questions, incorrect applicant values, visible validation errors, and unsupported required fields. They use a mocked submit action only. The live Broadsign DRY_RUN result above is separate DOM evidence; it did not submit anything.

## Reliability and safety

The scalability objective is thousands of boards and hundreds of applications per run. Use bounded concurrency, rate limits, retries, checkpoints, resume-safe recovery, and duplicate prevention. Never invent answers, bypass CAPTCHA/access controls, or commit resumes, profiles, sessions, tokens, or runtime data to public Git.
